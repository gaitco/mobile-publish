# Project Publishing Policy Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task after user approval. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** جعل طلب رفع تطبيق يستخدم mobile-publish تلقائيًا، مع قرار نشر ثابت لكل مشروع وعزل صلاحيات كل مطوّر، دون إدخال Shorebird في مشروع لا يريده صاحبه.

**Architecture:** مهارة مشتركة واحدة، وسياسة غير سرية داخل كل مشروع، وبيانات وصول مستقلة على جهاز المطوّر أو داخل CI. يحدد المشروع محرك البناء؛ تحدد الصلاحيات أين يمكن تنفيذ النشر. نقص الأداة أو الحساب لا يغير محرك المشروع.

**Tech Stack:** مهارة Codex/Claude Code الحالية، Bash/Python، إعداد JSON للمشروع، GitHub Actions واختبارات السكيل الحالية على Linux وmacOS.

**Spec:** طلب المستخدم في هذه المحادثة بتاريخ 2026-11-11. هذه خطة مقترحة للمراجعة؛ لا تتضمن موافقة على تنفيذ أو تغيير حسابات أو نشر تطبيق.

## Global Constraints

- الطلب الحالي تخطيط فقط؛ لا تعديل للسكيل أو تعليمات المستخدم العامة أو إعدادات المشاريع، ولا commit/push للخطة قبل المراجعة.
- كل طلب رفع **تطبيق موبايل** يبدأ بمهارة mobile-publish؛ لا ينطبق على نشر باك إند أو موقع أو ملف.
- اختيار المهارة تلقائيًا مستقل عن قرار استخدام Shorebird.
- دومينو مثال صريح لمشروع نشر عادي لا يُركّب عليه Shorebird.
- استخدام Shorebird في ERP قرار لكل مشروع باسمه؛ لا يعمم على كل تطبيقات ERP ولا يتغير آليًا حسب عدد المستخدمين.
- لا تغيير اشتراك أو فوترة أو عضوية فريق أو إصدار مفاتيح أثناء الرفع الروتيني.
- لا نسخ أسرار من جهاز إلى جهاز أو وضعها في Git أو ملف سياسة المشروع.
- في OTA: Android وiOS يجتازان dry-run ومقارنات native/assets والفحوص اللازمة قبل نشر أي منصة؛ لا تجاوز للتحذيرات ولا تحويل تلقائي إلى إصدار متجر.
- الحفاظ على تعديلات المستخدم، إعدادات البناء والتوقيع الأصلية ومسارات النشر الموجودة.

## Review Focus

1. مطوّر بلا Shorebird ينشر مشروع Flutter عادي دون أي استدعاء Shorebird أو قراءة أسراره.
2. مشروع Shorebird على جهاز بلا صلاحية يتوقف قبل التنظيف/البناء، دون تسجيل خروج أو تغيير حساب أو fallback.
3. تعارض السياسة مع إعداد Shorebird أو الإصدار الفعلي لا يُحسم بتجاهل أحدهما.

5. اختلاف نسخ السكيل أو تعديلها محليًا لا ينتج تحديثًا قسريًا أو حذفًا للعمل.

## Decision Contract

يقترح ملف `mobile-publish.config.json` في وحدة التطبيق، متتبعًا في Git، يحوي:

```json
{
  "schema_version": 1,
  "runtime": "flutter",
  "stores": ["play", "asc"]
}
```

هذا مثال للشكل فقط؛ قائمة المتاجر تُثبت من إعدادات كل مشروع، لا تُنسخ للجميع.
`runtime` يقبل `flutter` أو `shorebird` فقط، و`stores` قائمة غير فارغة من المتاجر المدعومة دون تكرار. لا أسرار ولا إيميلات دخول ولا كلمات مرور.

| حالة المشروع | القرار |
|---|---|
| سياسة Flutter متسقة مع المشروع | بناء عادي، دون حاجة لأداة أو حساب Shorebird، ودون تثبيته أو تهيئته. |
| سياسة Shorebird متسقة مع المشروع | التأكد من الأداة والحساب والصلاحية للتطبيق المقصود أولًا، ثم مسار Shorebird. |
| Shorebird مطلوب لكن وصول المطوّر ناقص | استخدام CI موثوق ومهيأ مسبقًا لهذا التطبيق إن توفر؛ وإلا توضيح الناقص والتوقف قبل أي عملية نشر. لا نقل للمفاتيح ولا fallback. |
| ملف القرار ناقص | فحص الإعدادات ومسارات النشر والإصدار المثبت/المتجر لتجهيز تصنيف أولي. إذا كان نشرًا عاديًا مثبتًا بلا أي إشارات Shorebird، يستمر كالسابق. إذا بقي تعارض أو غموض، يُحسم مرة واحدة قبل النشر ويثبت القرار. |
| سياسة Flutter مع إعداد/إصدار Shorebird فعلي، أو العكس | تعارض يمنع البناء. يعالج بتدقيق مستقل؛ لا إزالة أو تركيب Shorebird آليًا. |
| طلب OTA لمشروع Flutter | توضيح أن الإصدار لا يدعم OTA؛ لا تركيب Shorebird ولا تحويل الطلب إلى نشر متجر تلقائيًا. |

السياسة لا تحول تطبيقًا مثبتًا من runtime إلى آخر. أي تركيب أو إزالة Shorebird له نطاق وموافقة مستقلان. لا استنتاج من عدد المستخدمين ولا تغيير تلقائي عند زيادته.

## Acceptance Criteria

- طلب «ارفع» داخل مشروع موبايل يختار المهارة بعد تثبيتها وتعليماتها؛ إعداد الجهاز لا يختار runtime.
- دومينو وأي مشروع Flutter عادي لا يتصلان بـShorebird ولا يحتاجان حسابه ولا يُركّب عليهما.
- مشروع Shorebird يحتفظ بمحركه، ونقص وصول مطوّر لا يغير المشروع أو يعطّل قدرة OTA للإصدارات الجديدة بصمت.
- السكيل ليست ترخيصًا أو حسابًا: تنزيلها لا ينقل صلاحيات المستخدم أو أسراره إلى عبد الله.
- تحديث المهارة قابل للتكرار ويحافظ على العمل المحلي ويكشف اختلاف النسخ.
- كل فحوص الجاهزية التي يمكن إثباتها تسبق البناء، وتبقى قيود التوقيع والمعالجة والمتاجر معلنة بدقة.
- كل الاختبارات ناجحة على GitHub على النظامين لنفس التحديث، مع روابط الدليل؛ لا تجاوز لفحوص OTA.
- لا تنفيذ حاليًا: هذا الملف هو ناتج التخطيط الوحيد، ولم تتغير قواعد النشر أو المشاريع.
